# 剧本 3 · HR 招聘周期——陈静与后端工程师岗位的六周

> 设计压力测试 · 对照 `docs/终极形态设计方案.md`（v3.6，唯一设计事实来源）· 2026-08-17
>
> 主角：陈静，120 人科技公司 HR 招聘专员，同时推进后端工程师 / 产品经理 / 测试工程师三个岗位，DSH 操作者（agent 显示名"云小助"）。
>
> 织入探针：① 六周流程任务 vs 话题=会话；② 多方面试编排与改期（操作边极限）；③ 候选人=组织外实体；④ 多面试官反馈聚合与催收；⑤ offer 走云之家既有审批流；⑥ 入职 checklist 跨部门；⑦ 每周五跨岗位管道周报。
>
> 人物：老周（研发总监/用人经理）、王磊（后端 TL）、赵敏（架构师）、孙浩（高级后端）——面试官；林宇（候选人 A，入职）、郑凯（候选人 B，爽约）、吴迪（候选人 C，谈崩）；方琳（HR 经理）；小杜（IT）、阿雅（行政）。

---

## 一、剧本（六周，取关键日）

### 第 1 周 · 周一：需求落地

早上 9:40，研发总监老周在「后端岗-招聘协同」群里甩出一段话："急招一名后端，Go 为主，要分布式经验，P6 左右，最好一个半月内到岗。"群里有陈静、老周和三位未来的面试官——后端 TL 王磊、架构师赵敏、高级工程师孙浩。

陈静回了个"收到"，然后 @云小助："按老周的要求起草 JD，参考知识库里上次 Java 岗的模板；另外建一张岗位管道表：阶段列 初筛/一面/二面/终面/谈薪/offer/入职，候选人逐行记录。"

agent 在话题里回帖 ack——"收到，回复本条消息可在此任务上继续"——十分钟后交付 JD 草稿文档和管道多维表格，附过程摘要。老周在话题里直接改了两处任职要求，agent 更新，老周回"可以"，任务验收归档，话题从侧栏退租。

顺畅。但陈静把 JD 挂上招聘渠道时意识到一件事：她刚委派并验收的是"写 JD 和建表"这个**动作**，不是"招到一个后端"这件**事**。后者要六个星期、几十个动作。她本能地想在工作台找一个"岗位"级别的东西——能装下整条流程、显示"现在走到哪一步"的容器——没有。收件箱里躺着的是话题，话题的粒度是一次委派。她最终接受了现实：**管道表格就是那个容器，话题只是她每次伸手的把手**。她把表格链接钉在了自己的浮窗便签上。

同一天，产品经理岗和测试岗各有各的群、各的表。三条流水线，三个互不相识的场所。

### 第 1 周 · 周五：第一次周报

下午四点半，HR 经理方琳照例要三个岗位的周报。陈静在后端群话题里问云小助："汇总本岗位管道现状。"agent 读表格：投递 32、初筛通过 9、约面 3，顺手把上周新增和转化率算了出来。另两个岗位她得分别去各自的群再问一遍，然后自己把三段拼成一条消息发给方琳。

她试着问："能不能每周五下午四点，自动把三个岗位汇总好发我？"agent 如实回答：定时主动汇报当前不支持，随时问随时答。陈静记下了自己的新例行公事：每周五，三次提问，一次手工拼接。

### 第 2 周 · 周二：约一面——五个人的日历，和一个不在日历里的人

第一个进面的是林宇。一面要王磊、赵敏、孙浩三人加一间能视频的会议室。以前这活儿够陈静在日历里翻半小时，现在她一句话："约林宇一面，一小时，周四或周五，三位面试官都在，订会议室。"

agent 查出三人空闲交集，给出三个候选时段并配好每段可用的会议室——这一步漂亮得让她想起设计文档里"筹备员"那个词。但下一步卡住了：**林宇不在云之家里**。agent 没有任何办法触达他——没有邮件面，没有短信面，日程邀请发不出组织之外。陈静打电话跟林宇敲定周四 14:00，回到话题里转告 agent，agent 才落日程：三位面试官进参会人，订下三层会议室，把简历和 JD 链接写进日程说明——面试官在原生日历里点开就能看。最后陈静让 agent 起草面试确认函，她复制进自己的邮箱发给林宇。

"你能搞定五个人里的四个，"她对着屏幕嘀咕，"偏偏第五个才是主角。"

### 第 2 周 · 周四：放鸽子

候选人郑凯约的是周四上午 10:00。10:12，王磊在群里问："人呢？"郑凯没来，电话不接。三位面试官在会议室干坐十五分钟散场。

云小助对此一无所觉。日程到点、会议没发生——在它那里没有任何区别，没人喂给它，它就不知道。更微妙的是，陈静上周五其实委派过"约郑凯的一面"并且已经验收归档了：从任务的视角看，"约面"这件事做得完美无缺，日程建了、会议室订了、材料齐了——**任务的成功和现实的失败各记各的账**。陈静事后 @ 它：取消日程占用、管道表把郑凯标"爽约-关闭"、给三位面试官发致歉说明、把候补的吴迪提上来。这些它都利落做完。但陈静看清了一个角色分工：**她是 agent 的传感器**——凡是发生在日历格子之外的现实，都要她亲手搬进会话图。

### 第 3 周 · 周一：改期连环

上午 9:20，王磊在群主楼说："线上出故障了，下午林宇二面我到不了。"这句话没 @ 云小助，agent 毫无反应。陈静看到消息，转身委派："王磊下午来不了，二面改期，重找王磊赵敏加老周的交集，要会议室。"

重排本身 agent 做得干净：新交集、新会议室、旧日程改时间而非删重建，材料链接原样保留。但外部的另一半又来了——改到周三 15:00 得林宇同意，又一通电话；改期确认函，又一次复制粘贴。**内部编排丝滑如水，组织边界像一堵墙，墙外每一步都是人肉。**

### 第 3 周 · 周三：反馈收集

林宇一面完成。陈静委派："建反馈表，三位面试官每人一列：结论/亮点/风险/评分；私聊把链接发给他们，今天内收齐。"

agent 用专号分别私聊三人。王磊、赵敏当天填了，孙浩没动静。次日早上陈静问："收齐了吗？"——"孙浩尚未填写。"第三天早上，同样的问答。**agent 不会自己去催**——到期跟催不在它的能力域里。最后是陈静在走廊拦住孙浩才收齐。

她还注意到一个细节：赵敏没填表，而是在自己与云小助的私聊里直接说了一段评价。那段话住在"赵敏×agent"这个场所里，并不会自动流进后端群这边的任务；是 agent 把它誊进反馈表，信息才算归队。**表格是唯一让三股输入汇成一股的地方。**

### 第 3 周末－第 4 周 · 周三：等老周的三天

林宇二面周三完成，老周周四飞客户现场，终面意见就此悬置。周五没有，周一没有，周二还没有。

这三天在工作台上是一段奇怪的空白：任务不算完成，也不在"待确认/待验收"里，它就安静地停着。收件箱教她认识了三种状态——待确认、待验收、运行中——可"等一个出差的人开口"哪种都不是。**没有任何地方写着"此任务在等老周，已等待 3 天"。**陈静每天点开话题翻两遍，像盯一口不响的锅；她甚至问过 agent"现在卡在哪"，agent 答得没错——"等待周明轩的终面意见"——但这个答案只在她想起来问的那一刻存在，问完即散，不挂在任何看板上。周二晚上猎头传话：另一家公司给林宇发 offer 了。她连发三条私聊催老周，周三上午等到一句"过，薪酬按 P6 中位往上谈"。她想：如果"在等谁、等了几天"能像待审批那样明晃晃挂出来，她至少不必拿焦虑当提醒器。

### 第 4 周 · 周四：谈崩一个

同期走到谈薪的还有吴迪：期望 35k，老周批的带宽上限 30k。薪资数字、审批带宽，绝不能出现在有面试官的群里——陈静全程在与 agent 的**私语态**里作业：让它整理吴迪的薪资历史、市场分位参考、两套谈判方案。两轮拉扯，吴迪拒了。她让 agent 把管道表标为"薪资未谈拢-关闭"，又在私语里补一句："记住：P6 后端带宽上限 30k，低于市场 75 分位；后续候选人预期超 32k 的，提前给老周打预防针。"公私两条轨道在这一段泾渭分明——这是整个系统里最让她安心的部分。

### 第 5 周 · 周一：offer 审批——另一个宇宙

林宇谈妥 31k，超带宽 1k 需特批。offer 审批走公司在云之家上现成的审批应用：用人经理 → HRD → CFO 三级。

陈静原以为这是 agent 最该接手的环节——填单、提交、盯流转。结果发现 **agent 对审批应用完全无感**：它嘴里的"审批"是它自己写操作前找陈静要的那个确认，跟企业审批流是两个世界。她手动填单提交。此后三天，单子走到哪级、卡在谁手里，agent 一概不知，她每天自己点开审批应用看。周三 CFO 批了，她把结果告诉 agent，agent 更新管道表——又一次，人肉传感器。

### 第 5 周 · 周三、周四：入职准备

林宇接了 offer（邮件，仍走陈静的邮箱），定下下周一入职。陈静委派："建入职 checklist：笔记本、工位、域账号、邮箱、门禁卡、合同打印，六项，负责方 IT 或行政，逐项可打勾；把需求发到 IT 服务群和行政群。"

第一个磕绊：云小助在 IT 服务群**还没开通接单**——那个场所的合同从没配置过。陈静去设置页给两个群开了最小权限（发消息+只读）。agent 把 checklist 链接和需求发进两群，IT 小杜回"收到"，行政阿雅约周五装工位。之后的追踪陈静学乖了：她不指望 agent 从别的场所替她盯回复，而是要求所有人**直接在 checklist 表格上打勾，agent 只看表格**。表格再一次成为跨部门的总线。到周五，六项完成四项，域账号和门禁卡挂着。

### 第 6 周 · 周五：就绪检查与第六次周报

入职日程定在下周一 9:30。陈静在对象面点开这条日程——事件枢纽显示：参会人、会议室、关联 checklist **就绪度 5/6**，门禁卡未闭环。她让 agent 在行政群发跟进，阿雅回"周一早上一定好"。

下午四点半，第六次周报。她熟练地三个群各问一遍、拼成一条发方琳，前后二十分钟。发完盯着屏幕想：**这句话我用几乎相同的措辞说了六遍，时间、格式、收件人全都不变——这台号称替我做事的机器，差的其实不是能力，是一个日历上的闹钟。**

### 入职日（第 7 周 · 周一）

9:20 林宇到前台，门禁卡 9:00 刚办出来，设备账号工位就绪。中午陈静在话题里发："/done 林宇已入职，岗位关闭。"话题归档，agent 蒸馏了几条记忆进后端群的场所记忆：面试官池、反馈平均延迟两天、薪酬带宽教训。

陈静看着那几条记忆忽然想到：下周启动加急的测试岗在**另一个群**。这六周学会的一切——催反馈的节奏、谈薪红线、入职 checklist 的坑——都住在后端群的记忆里，跨不过去。**六周的复利，被场所的墙切成了三份。**

## 二、逐环节走查缺口表

缺口分类：缺失 / 不合理 / 已知推迟-域F / 已知推迟-移动 / infra上限。严重度：高 / 中高 / 中 / 低。

| # | 剧本环节 | 用户期望 | 设计现状 | 缺口分类 | 严重度 | 第一性判断 |
|---|---|---|---|---|---|---|
| 1 | W1 岗位立项："招到一个后端"整体委派 | 有"岗位/流程"级容器：装下六周几十个子动作，显示走到哪一步 | 会话图节点只有 session/任务/审批/工件/记忆（§1.1）；话题=会话的粒度是一次委派（§1.7）；串行队列 + `/new`/`/fork` 管上下文不管流程；流程状态事实上寄生在管道表格里 | 缺失（概念层） | 高 | 话题=会话回答了"上下文放哪"，没回答"跨几十次委派的工作放哪"。剧本表明设计已隐性给出答案——管道表格就是流程真身——但未升为一等原则：工件应可声明为"活的工作对象"（带状态、被多会话读写、可聚合查询），会话只是它的操作台 |
| 2 | W2 约一面（内部编排） | 3 面试官交集+会议室一步约齐 | D8 操作边 7 工具（参会人/空闲会议室/description 落材料），筹备员模式——完整覆盖 | 无缺口（亮点） | — | 五边模型的操作边经多方编排压力测试成立 |
| 3 | W2/W3/W5 候选人触达（约面、改期、确认函、offer） | agent 直接触达候选人（邮件/短信/组织外日程邀请） | 采纳轴只覆盖"组织内未装者经云之家原生消息触达"（§1.2）；候选人在组织通讯录之外，41 工具无 email/SMS 面；外部触达全程人肉+复制粘贴 | 缺失 | 高（全场最高频） | 会话图的宇宙以组织通讯录为边界，而招聘/销售/采购类工作约半数参与者在宇宙之外。"外部参与者"需成为一等实体——哪怕只是**出站单向投影**（agent 起草→确认→经操作者信道发出→回执人工回填的结构化闭环），也远胜完全缺位 |
| 4 | W2 郑凯放鸽子 | 会议没发生，agent 应感知并善后 | 日程执行结果无感知；无 no-show 语义；时间触发（触发边 push）归域 F；善后动作被委派后可做 | 已知推迟-域F | 中 | D8 说"日程是关于未来注意力的契约"——契约的**违约**本身是高价值信息。推力依赖调度器，推迟合理；但可先补 pull 版"会后确认"语义（委派时挂"会后问我结果"钩子），不需要调度器 |
| 5 | W3 王磊群内说"来不了" | 群里说一声 agent 即响应改期 | 未 @ 不触发；盯群/轻问归域 F（A0 边缘案例已裁决推迟） | 已知推迟-域F | 中 | 裁决正确：未经 @ 的介入是主动性，信任未建立前不做；代价是操作者当转发器，可接受 |
| 6 | W3 改期重排（内部半段） | 改时间不重建、材料保留、各方日历即时更新 | event_update + 参会人/会议室重查——覆盖 | 无缺口（亮点） | — | 重排的算力不是瓶颈，触达半径才是（见 #3） |
| 7 | W3 反馈收集与聚合 | 三人反馈自动收拢、可对比 | 专号 DM 发表格链接可行（P2）；表格聚合可行；但 DM 自由文本回复落在各"联系人×agent"场所，与任务所在群互不可见（C1 记忆跟场所走；会话互读限同场所） | 部分覆盖；跨场所信息路由缺失 | 中高 | agent 誊表暴露隐性架构：**工件是唯一合法的跨场所信息总线**。应从隐性升为显式原则（"跨场所协作走工件，不走会话"），并为"任务发起的定向询问→回执归队"设计受治理的回路 |
| 8 | W3 催收孙浩 | 未填者被自动提醒直至收齐 | 到期跟催明确归域 F | 已知推迟-域F | 中高 | 催收是流程型工作频次最高的动作（占陈静人肉动作约三分之一）。有界的"任务内跟催"（明确等待对象+明确期限+操作者显式立约）风险远小于开放式主动性，可在域 F 内部分层先行 |
| 9 | W3-W4 等老周三天 | "此任务在等谁、等了多久"可见 | A1 等待可见仅覆盖"等操作者写确认"；等第三方人类输入无状态对象、无展示、无时长；任务落在收件箱三态（待确认/待验收/运行中）之外的沉默区 | 不合理（概念覆盖过窄） | 高 | A1 的第一性是**阻塞归因**，而阻塞源天然不止操作者。把"等待"泛化为图对象（等谁/等什么/自何时起）是纯图对象层扩展、零 infra 依赖，直接命中"组织信任度=敢等待"因子——现有设计里性价比最高的一处修正 |

## 四、最重要的第一性洞察

**话题=会话回答了"上下文放哪"，没有回答"工作放哪"。**

陈静的工作对象是"岗位"——一个横跨六周、横跨多个场所（面试官私聊、IT 群、行政群、审批流）、横跨组织内外边界的流程。而会话图里没有任何节点对应它。剧本里所有高严重度缺口——等待归因（#9）、跨场所聚合（#7）、周期汇总（#14）、跨部门追踪（#12）、中期蒸馏（#16）——本质上都是同一个缺位的投影：**流程没有真身**。

关键在于，剧本同时证明设计已经无意中给出了答案：陈静六周里每一次自救，靠的都是那张管道表格——它是流程状态的唯一权威、三股反馈汇流的唯一河床、跨部门协作的唯一总线、周报的唯一数据源。这与 §1.5"会话是交互单元，工件是工作单元"完全同构，只是设计尚未把它推到底：**工件今天只被当作"产出物"（流的沉淀），而流程型工作需要它成为"活的工作对象"——可声明状态、可被多个会话与场所读写、可挂等待对象与期限、可被聚合查询。**

因此第一性解法不是新建项目管理子系统（那是把 Motion 式越界换个方向重犯），而是一次升格：承认"工件为总线"是跨会话、跨场所、跨内外边界工作的一等架构原则，让会话安于操作台之位。会话图缺的不是新 surface，是一类节点。
