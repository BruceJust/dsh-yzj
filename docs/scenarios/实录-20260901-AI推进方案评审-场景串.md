## §0 总览：会上真正串起来的那条链

会议开场演示的是**一条只走了一半的链**，后面 1 小时全在补它的另一半。完整骨架长这样：

```
[工作现场]                    [AI 推进]                       [工作现场]
 IM 群 / 会议纪要  ──订阅──▶  发现 or 主动创建 ──拆解──▶ 派活给人 / 让 AI 做
 新建任务 / 对话                    │                              │
      ▲                             │                        受领三态（接/拒/要前置）
      │                             ▼                              │
      └────────────执行回工作现场◀── 待验收 ◀──产物+证据──────────┘
                                    │
                              对照标准校准 → 确认完成并归档
```

**会上一致认定「断」的三处**（后面每条验证用例都指向其中之一）：

1. **回程断**：产物在工作现场产生了，回不到推进；推进里点一下，也进不到工作现场执行。
2. **视角断**：整个原型用一个账号讲派活人和接活人两个视角，接活人那半条链**完全没画**。
3. **证据断**：会议开完了算不算完成？纪要能证明什么？没有产物时凭什么打勾？

## §1 场景串

### S1 · AI 发现卡片的四选一处置（00:00–06:05）

**情境**：系统在"AI 发现"区推给我一条卡片（例：某条待推进事项）。

**链路**：
1. 卡片上三个主操作：**让灵基做** / **转为推进（跟进）** / **忽略**
   - 「转为跟进」= 转到我自己名下，跟我相关
2. 点「忽略」不直接消失，弹出**四个原因**（类比灵基点赞点踩后的浮窗）：
   - ① **判断不准确**——且能指到"是哪条依据不准确"
   - ② **这个东西不归我管**
   - ③ **已经在别的地方跟进了**（AI 发现的这条与别处重合）
   - ④ **还没到开始的时间**（"暂时不用"）
3. 选完点「提交并忽略」→ 该条被忽略；也可以**不给原因直接忽略**（说话人 1：所以实际是五个选项）
4. 被忽略的条目可从「已完成 / 已忽略」页签**捡回来**（说话人 3 提出，说话人 1 确认）

**「忽略」与「暂时不用」的区别**（说话人 2 追问两次才问清）：
- 暂时不用 = **过一阵子再推**。原话例子：*"今天本来要开个会，但我觉得不该上午开，该下午开，所以我告诉你我上午先不参加。"*
- 忽略 = 默认不管了。**"后面的机制还得看"**——即忽略是否等于"再也不推"，会上未定。

**交互形态差异**（05:23 说话人 1 解释设计动机）：
- 「我的推进」+「协作请求」= **平铺**，点击直接在右侧看详情
- 「AI 发现」+「已完成已忽略」= **折起来成 list**
- 理由三条：AI 发现的单条内容太少；给它单独菜单则页面利用率很低（首页已有四个大板块）；用户真正关心的是前两块。

**断点 / 缺口**：
- **推送节律没有告诉用户**（说话人 1，06:21）：*"我每周一早上 9 点开周会——只要你把规则定下来用户就知道了。而不是周一让我开个周会，周二突然又让我开，下周一又不开了。这种对用户来说他没有安全感。"* → AI 发现必须有**可预期的规律**（每天几点推 / 时时刻刻推），且**在首启动页告诉用户"我拿了你哪些数据"**。目前这些信息一条都没有。
- 反复忽略后如何**避免重复推荐**、如何**防打扰**——说话人 3 承认只是设想，规则未定。

### S2 · 派活→交付→验收：张琪的《IM 接入方案》（07:42–12:15）

这是会上唯一走完的一条链，也是所有后续讨论的锚。

**链路**：
1. 我（派活人）在推进里，**AI 建议这么拆分任务，并给我挂好了相关的人**（张三、李四、王五）
2. 点「全部推送」→ 这几个人在**各自平台的「协作请求」里收到**
3. 接活人有**三种行为**（07:42 说话人 1 原话）：
   - ① 接受
   - ② 拒绝
   - ③ **我要做，但需要你先提供一些东西给我**（前置依赖）
4. 张琪做完了，状态显示"已反馈"
5. 我点进去看反馈 → **AI 在 IM 里识别到张琪发的那份 MD 文档《IM 接入方案》**，判定"这个产物跟 AI 推进里的任务是相连的" → 归为那边的产物
6. 我判定是否闭环 → 唯一按钮：**「确认完成并归档」**

**关键问答**（10:21，说话人 2 → 说话人 1）：
> 问：*"是这个人发的吗？他是这个人发也行……到底是他盖还是点击盖，你这边是不关注的，是吧？只要是盖完结果的就行。"*
> 答：*"是，因为责任人是张琪。"*
> → **不关注产物由谁触发上传，只认责任人 + 结果。**

**AI 的介入点**：*"到底怎么用 AI 去检测这一个文档、检测它这个成果是否符合了我当前这个任务的标准"*——说话人 1 明确标注这是**扩展内容，是否要做待定**。

**不确认时的路径**（11:07–11:55）：
- 我不确认完成 → **继续跟他对话**："整体方向有问题，你要改什么东西"
- 状态**停在待我确认**
- 两个未定问题：
  - 是否记录**第一版和第二版的匹配度**？
  - **我不点确认、直接发一句话，是否等于默认"方案没通过，你继续改"**？（说话人 1 倾向是；未裁决）

**断点 / 缺口**（说话人 2，11:55）：
> *"这个地方你应该有个明确的提醒。我在这里你没有引导，我其实不知道该怎么操作。如果我是个新用户，我这堂课感受就只能'确定'。但其实作为普通用户，你没有引导的话，我怎么在这要说一句话？"*
→ **只有"确认完成"是可见的，"打回"这个动作在界面上不存在。**

### S3 · 拒绝回流：陈川拒了这条任务（12:15–13:50）

**链路**：
1. 陈川拒绝了任务。**拒绝理由被带回**：*"这块实际上是季度规划，本周做不来，下周建议评审会上一起定。"*
2. AI 识别到拒绝 → **把这个事情回流给我**（派活人）
3. 我有**三种处置**：
   - ① **改派别人**
   - ② **我自己来**（→ 关联推进的责任人变成我）
   - ③ **撤销**（这条任务不要了）

**断点 / 缺口**（说话人 2，13:05，会上最完整的一条设计要求）：
> *"撤销这条，它可能会对你的整体目标产生影响。它应该还有一个二次提醒：你这边撤了之后会对你这里产生什么影响？确定要撤销吗？**或者说你确定撤了之后，我的目标也要同步修改**。因为你撤了之后目标不修改的话，它永远这个任务完不成。"*
→ **撤销必须是"两段式 + 目标同步"，否则目标永远挂着一个完不成的洞。**

说话人 3 补充另一个撤销来源：*"有可能他撤销也是别人反馈了一个原因，比如我本来是要收某一个产物，他的产物已经有了。"*
→ **撤销要带反馈原因，不是一个静默动作。**

### S4 · 拒绝理由变成下一环：下周一评审会（16:19–17:17 / 36:23–38:16）

S3 的第 ③ 分支往下走，是全场争论最深的一段。

**链路**（说话人 3/4 演示）：
1. 我选「自己来」→ 那条子推进被改写成 **"下周一评审会上确定"**
2. 时间到，下周一开完评审会
3. **速记里出现了这场会的纪要**（内容是"关于红线的设置"）
4. **我的 agent 扫到"你已经开完这个会了"** → 卡片变绿："请查看会议纪要，已完成相应的会议"
5. 我点击 → **跳到速记里那份纪要** → 确认会上回复了相应意见
6. 我选「已完成」→ 跳回推进，那一项变成勾
7. 三处都打勾 → 整条推进关闭（"你是否已完成这个推进"）

**第一次反驳**（说话人 1，36:49）：
> *"等一下，会议跟已完成……会议又没产出什么东西，会议就是个记录而已。"*

**说话人 3 的两档回应**：
- **弱档**：开完这个会 = 打个勾就算完成（"这是一种我理解比较弱的方式，但也 OK"）
- **强档**：**一定要有相应的结论或产物挂进来**。会议类型的产物可能是纪要，或某个结论——"如果能精确到那个颗粒度，我理解它是可以打个勾完成这个子推进"

**说话人 2 的裁决**（38:24，本文件最重要的一段，直接可写成验收断言）：
> *"会议是其中一个订阅源。这个源它一定有产物，第一个产物就是会议纪要。**这会议纪要本身它只能确定一件事：这个事情你做了，或者会上面也聊了。然后到底有没有做完、或者做得好不好、是不是偏差了，是没有证据的。**所以会议这个源它可以提供一个**中等置信度**的东西，但它没办法证明一个事情是做完了。所以它会有一个标记：**会议上面提到了某某，但是他没有看到产物。在没看到产物之前，他不能认为这个推进已经完成了。**"*

**由此逼出的新问题**（38:24 结尾）：
> *"那这时候就涉及另外一个点：我如果选择会议的切片，我在哪里上传我的产物呢？"*
→ 直接引出 S5。

**说话人 7 补的自动路径**（39:28）：
- 一次会议结束 → 推进自己去检测"我当前这个推进有哪些产物出现"
- 只有一条会议纪要 → **AI 判定"不足以支撑这个推进/待办完成"** → 给建议，两选一：
  - ① 找谁去生成这个文档
  - ② 再安排一个子推进给谁 → 出现在那个人的协作请求里
- 如果是我自己完成：**直接让灵基做 → 生成产物 → 这个会话就变成这条推进的一个源** → 那条完成

### S5 · 会前/会中/会后的证据在哪产生（01:00:26–01:04:55）

**说话人 2 立的规矩**：**每个工作现场的证据形态不一样，要分别定义"产生什么证据、证据存在哪、怎么检测"。**

| 工作现场 | 证据形态 |
|---|---|
| IM 群 | 群里发的**文件** + **群聊记录**（两者都可作为完成的证据） |
| 会议 | **会议纪要**（唯一自然产物）+ 会前材料 + 会中材料 |
| 会议（业务型） | 例："我在看临机要 1 万家客户"这种业务会议——**有必要去取业务系统里的某个数据**，跟业务系统就有关系了 |
| AI 对话 | AI 产出的产物本身（例：生成的原型） |

**现实摩擦**（说话人 2 举本次会议自己举例）：
> *"你想象一下，比如你找我讲一个事情……他约了一场会，打开会议纪要，同时他向我展示了他的那份材料。**但材料现在没有入口上传，他只能通过投屏的方式来讲述这个东西。**"*

**说话人 3 承认的会议现场天然缺陷**：
- 会议的内容只有**纪要或转录**两样
- **关联文件极其稀少**——"大家一般比较少直接在这里面关联文件，看个人习惯"

**会后补证据的链路**（01:03:21 说话人 3）：
1. AI 推进识别到你开了这场会
2. 发现纪要**不足**——"你们只达成了'评审通过'，但我还不知道具体内容"
3. 提示"你需要补充设计方案"
4. 你从其他工作现场**关联进来**，或**直接在这里上传**
5. 两个勾都齐了（有纪要 + 有设计方案）→ 通知派活人 / 更新推进

**说话人 2 的收口**：**会前、会中、会后都可能需要上传入口，而且要让它自然发生。**
> *"现在的场景是，会前我组个会约个会，比如像邵杰这样，今天我开了会，昨天他已经把材料准备好了，他就直接丢群里面，这就是会议材料。但如果是纳入推进的话，**他怎么自然地把这些材料放到推进里面去？让它自然地发生。**"*

**引出的深层质疑**（01:04:55）：
> *"提那个问题本身有问题——就是我们是否觉得说会议跟 IM 是没法分开的？"*
→ 直接引出 S6。

### S6 · 一个群能不能当工作现场 / 订阅源（01:05:02–01:08:02）

**说话人 1 的提议**：IM 每个对话里都有 AI 速记入口 → **能不能把一个群整体作为 AI 推进的工作现场？**
> *"因为你里面大家会说话，会发产物，也会有会议——其实这些东西可能就是 AI 推进想要的。"*

**说话人 2 给出「订阅源」的完整定义**（01:05:42，本产品也缺这个名词的对位物）：
> *"AI 推进之所以能知道这个事情推进情况怎么样，取决于上游的一些信息。上游信息就有很多：比如一个群聊、群里的信息；比如某个会议的纪要；甚至比如我通过 AI 完成的某个产物——**比如你通过 AI 生成这个原型，这也是被 AI 推进所监测到的一件事，它识别到你完成了这个事情**。这些都是 AI 推进的订阅源。**包括 ERP，未来它会监测很多的源**，因为你的工作现场很多，在各种地方进行工作，所以它在各方面监控，最终实现这个事情的持续跟进和反馈。"*

**同时，说话人 2 明确判定群不是好的推进方式**：
> *"我们认为群这个东西，第一，它信息太多太碎；第二，它没有形成一个可持续跟进的点。**群解决了信息的输入和输出、各种信息的同步，但不解决事情的执行，也不解决这个事情是否做对了、做好了**，它是有缺陷的。而且群只是其中一个工作现场，它不代表所有的工作现场。所以才有 AI 推进存在的必要性。"*

**可见域问题**（01:10:49 说话人 5 提出，本产品的"最小听众"直接对位）：
> *"他也存在一个视角问题。如果我们在一个群里工作，如果这个东西只跟我的推进有关，**他这个提醒应该只能我看到，别人看不到**。"*

**说话人 1 的现实反驳**：
> *"即使别人看到、他不能做操作，其实也 OK 吧。因为群里有一个问题：**你上传到群里面的东西，目前在权限上是大家都能看的**，那个不是说张三来看、李四不能看。"*

**说话人 2 收口**：技术上能做（消息推送可按人），但**群本身的"信息过载、跟我相关的怎么捞出来"是 IM6 那条线要解的问题，不在 AI 推进这边**。

### S7 · 主动创建：从工作现场发起推进（20:54–23:14 / 31:48–34:30）

会上补的第一条缺失路径。**上一版原型里有，这一版被砍掉了，会上要求补回来。**

**三个入口**（说话人 3 投屏演示的上一版）：

| 工作现场 | 主动创建方式 |
|---|---|
| **IM 对话** | @灵基："把我跟张琪的对话上下文（关联最近 10 条 / 今天之内）变成一个我的推进"——**带上下文过去**，回复"已建成"，可跳转 |
| **会议 / 速记** | 一场会下面有多条待办，**跟我相关的可能只有 1/3**——"我只关心我的内容，把它转为我的推进"。入口挂在待办事项上，或直接进推进 |
| **新建任务** | 常驻入口 / 气泡提示，或聊到一半已发起任务后再建推进 |

**手动关联 vs AI 推荐关联**（20:25–20:54）：
- 说话人 1 问："那是我手动关联，还是 AI 能识别去推荐我关联？"
- 说话人 5 答：**"两种都可以"**，并给出理由——*"在开始做的时候他就关联上了，后面再去挂钩的时候就会更容易一些。**如果在大量的对话里面事后去找，就会相对麻烦一些。**"*

**说话人 2 对讲故事顺序的要求**（20:54）：
> *"我在讲这个链路的时候，一开始应该是从一个工作现场开始——比如我就在聊天，或者我就在做新建某个任务；建完某个任务、做完某个任务之后，**我发现这地方需要协同，我可以点击某个按钮，就开始推进**，他就会进入到推进环节，沿着推进环节往下走。这个故事大家可能更容易理解一些。"*

**上一版被砍的原因**（说话人 3，58:21 复盘）：*"之前那版本的方式，交互的方式太多的点点点了，太多的待确认字段——那样是不太 OK 的，但那条路径是需要把它补充回来的。"*

### S8 · 「让灵基做」的闭环 & 执行到底在哪里发生（43:22–49:53）

**说话人 3 演示的版本**（在推进内闭环）：
1. 点「让灵基做」→ **它本身也变成一条推进**（可短可长）
2. 灵基给出产物，挂在右侧
3. 我做个浅查 → 两条出口：
   - **采纳并归档** → 这条任务关掉
   - **退回修改** → 给它提示词说要改什么 → 让它继续做（覆盖 or 出第二个版本）

**反驳一**（说话人 5，45:02）：*"这个交互还不太完整……除非修改，其实很难理解。"* → 建议直接回到对话里。

**反驳二**（说话人 2/5，47:00–47:25，杀死这个设计的一击）：
> *"你在这里就需要完整的一整套交互逻辑，因为**还要上传文件**。"*
> *"比如说这里，假设这个任务是修改 PPT。你自己怎么选择 PPT 模板？假设是搞个金钥财报，**你还要 @，支持他 @ 金钥财报**。"*
> → 在推进里做执行，等于**把工作现场的前端再开发一遍**。

**说话人 2 的裁决 —— 工作现场与推进的分工定义**（49:25–50:25，本场最重要的概念裁决）：

| | 工作现场 | AI 推进 |
|---|---|---|
| 是什么 | **就是工作的地方** | **长链路** |
| 上下文 | **不维护整个任务的上下文** | **关注任务本身上下文的提取与消费** |
| 粒度 | **只关注单点、单次**：读一次会议、一次对话、一次跟 AI 的聊天 | 跨越多次 |
| 核心概念 | —— | **订阅源**（信息来自哪里）、**产物是什么**、**产物跟标准的校准** |
| 执行 | **执行在这里发生** | **执行让它回到工作现场去** |

**裁决后的正确链路**（01:08:39 说话人 2 完整描述，这是执行侧的目标形态）：
1. 我点击某条推进
2. → **直接拉到对话/任务里**，**预先帮我写好提示词**
3. → 把相关材料（**这次会议、之前讨论的东西**）作为**附件上传在提示词里**："这些是背景，这些是原因"
4. → **第一步不是马上做原型**：先做一份分析报告 / 先做一轮研究 / 或先给一个工作计划（要做原型需要哪几步：先了解背景 → 做用户研究 → …… → 最后做原型）
5. → 做完之后**回到推进里**——"这里可能都需要有某些按钮，比如这个东西如果是通过 AI 进来的，它就能有某个按钮，归到那个推进里面去"
6. → **要很丝滑的联动**，才能让用户自然地感知

**关于"执行感"的处理方式**（52:11 说话人 2）：
> *"那个（工作现场 vs 推进的关系）是基础原则，这个（执行感）是它的设计方向。你要先完成那个东西，**在不打破那个原则的情况下，你可以优化这个体验**，让他觉得这地方是可执行的。比如通过一些前端的交互、一些转圈圈、一些自动化的东西，或者 **AI 抛出的一些执行方案**，阶段性地弹出一些东西。"*

### S9 · 接活人视角：完全没画的那半条链（40:33–43:01）

**说话人 2 的问题诊断**：
> *"第一个视角是发起者的视角，第二个视角是执行者的视角。**这两个视角中间是怎么链接起来的？在这个交互图里面没有体现出来，就导致大家理解起来困难，全靠想象。**"*
> *"你这里面两个人用的是同一个角色……相当于说你只有一个账号来讲两个视角。……**全靠嘴巴去讲，但是我们设计需要一个完整的链路。你只能让他们想象，这个东西就会失控。**"*

**要求补的执行者链路**（42:13–43:01，逐条都是验证点）：
1. 执行者**登录进来**
2. **协作请求高亮**——他首先看到有东西
3. 他进来**看到哪些上下文**？
4. 他**在哪里提交他的成果**？
5. **从会议来的任务 vs 从 AI 对话来的任务，提交链路是不是不一样的？**
6. **极端情况：假设他没有工作现场**——"有可能是线下领导口头跟他讲了一句话"，这种怎么纳入？

（说话人 2 后来把第 6 类单独命名为**沟通现场**：*"还有一些隐藏的、不在攻击（工作现场）里出现的，比如领导交办的一句话，这种纯线下的、没留痕的，那这些怎么纳入？这些是沟通现场。"*）

### S10 · 用本项目自己做样本：从建群到群沉默（01:26:20–01:28:51）

说话人 1 起头、说话人 2 完整讲完的一条**真实历史链路**——这是整份转录里最适合直接拿去当端到端验证剧本的一段，因为它是已经发生过的事实。

**说话人 1 的观察**：
> *"如果说从 IM 里我们建一个群，**一般都会有一个目标**。这个目标 AI 是不是就能识别到？因为有这个目标，会衍生下来有相关的任务、就是节点——张三李四王五谁干啥。基于这个会议又会衍生 AI 速记……**所以其实有可能就是从你建群那一刻开始。**"*

**说话人 2 复述本项目的真实链路**：
1. 最开始**拉了个启动会**
2. 启动会**把大家拉到群里**——但**大部分人只是知晓，不是这个项目的参与者**，他们需要知晓所以在群里
3. 进群之后，**某两位是这个阶段的主要执行者**
4. 他们**内部又产生了一些会**——"理论上这个也要记录推进这个事项"
5. 工作形式：**先在群里聊 → 还单聊了一些东西 → 之后发了一个报告让大家都知道、大家一起看 → 大家都得反馈**
6. **又拉了个会，讨论一轮，又发现一些问题**
7. **接着继续修改，下次再更新一遍原型**——"做两次之后就已经稳定了"
8. 稳定后**转到开发同学去开发**
9. 群**慢慢沉默**

**关键洞察**（01:28:00）：
> *"那个群会一直存在，直到这个东西相对比较收敛、比较稳定，大家去忙别的，这个群就开始沉默了。其实那就意味着那个推进可能就开始结束了。**但那个群没有"开始结束"的概念，它会一直存在那里。但推进它是有结束的**——比如你的原先设计子任务已经结束了，子推进已经结束了，你那边就收敛了，你就能看到你的任务结束了。"*

**这段总结出的双向要求**（01:28:51）：
> *"想讲的是工作现场的关系跟推进的关系，怎么帮助用户建立这种、或者说**不需要他经营**，这样自然地知道这种形式。**他在工作现场能自由地去推进里面看他的任务，他也能从任务里面随时地回到工作现场开始执行**——这两点是要看清楚的。"*

**一个群承载多条推进**（01:29:24）：
> *"设置到 IM 里面，他可能就要再承接一个、再展示一个还要推进的事情，因为那个 IM 可能**承载若干个推进**。每个人看那个群里面，**每个人自己的推进是不一样的**。总的可能是有一个下面的路该怎么走的问题。"*

## §5 价值口径与成本约束（决定验证的优先级）

### 生手用户的两条致命质疑（说话人 8，01:40:28 / 01:45:58）

> ①*"我第一个感觉是觉得**工作现场跟推进非常割裂**。……你说我主要可能进来又在这能看到，又在这能去点，就会让我觉得你要在哪操作？而且**你这两个之间它的信息怎么同步的**？如果我是一个刚进来的用户，可能会不太理解。**我不会马上认为说我在灵基上发的消息就能立刻同步到推进那边。**"*
>
> ②*"我们现在要讲一个价值、明确一个问题：**我没有用 AI 推进的时候，用灵基给我做一个报告；和我用了 AI 推进之后，我让灵基帮我做一个报告——这两个有什么区别？目前是没有区别。**"*

说话人 2 对这两条的处理方式（值得记下来）：
> *"他保留着赤子之心。**他讲的问题就是问题，他讲的问题一定是问题。他只负责提出问题，我们不需要解释问题，我们只需要解决问题。**"*

### 产物归属之争（01:44:17–01:45:44）

说话人 1 的立场（这是"AI 参与感"问题的根因）：
> *"虽然是 AI 搞的，但是有人为在跟 AI 沟通，实际上是 AI 协作给我的。……那个东西理论上不是灵基产的，**是我产生的产物**。因为**最后问责肯定问的是我，不会问灵基**。"*

说话人 2 的回应：*"所以他提出的价值点就是**怎么证明这东西帮我加速**。在我原始的设计之初，AI 干的那部分也算是 AI 推进的；但是在你的心智里，那不算是灵基帮你的。"*

### 已被认可的唯一差异点（说话人 8 转述，01:47:13）

> *"可以不断地把信息同步过来——**我在这个项目里，在哪个聊天里提到哪个信息变更了、可能对这个项目有影响，它会及时地有这个推荐、帮我转**。这肯定是我没用推进之前和用推进之后的一个差异点。**再差异点，目前这一版本是没有体现出来的。**"*

### 商业价值口径（说话人 2，01:30:03–01:31:07）

> *"AI 推进解决的问题是很明确的：比如我们做交付项目，**跟销售信息不对称导致的交付失误，产生的沉没成本——这个东西预先由 AI 推进发现、识别并且降低，这是它的核心价值。客户为的是"避免某项事故的发生"而买单。**后面还有沉淀啊、加速啊，这种也在里面，但只是次要。"*
>
> 佐证案例：*"某新房项目因为某些问题导致交付风险、用户投诉……**一次性损失 400 万**，他愿意为此花个十几万，这是没有问题的，因为他至少可以省回一两百万。"*

### 流程二分（说话人 2，55:36–56:43，本产品同款论点）

> *"企业这边有两种流程：一种是**企业已建立的标准流程**，高频的、重复的，走个流程就完了。另一种流程就是像我们现在这样的，**它可能没流程**——我们在探索的过程，但探索本身就是需要协作、检查和推动的，这就是 AI 推进要发现的。**而且这种流程是大量存在在我们这样的企业里面的**，它甚至可能孵化某个标准化流程。"*
> *"报奖这个环节是流程，但前期的创建、探讨、脑暴的过程是没办法沉淀的，**那个部分是很有价值的，也是应该被看见的**。……我做了很多的过程，失败的也好、成功的也好，都没被记录、都没成为组织资产。**这个就是组织的损失。**"*
> *"实际上我们能建流程的就是些标准流程，**非标流程是大量存在的，但是隐形的、高摩擦的**。"*

### 成本约束（01:31:07–01:33:59）—— 直接影响验证时的模型/频率设计

> *"现在已经有销售反馈了，说现在一个 token 成本太高，没有人敢用。**做一个报销花 100 块钱的 token 消耗，现在就不报销了，还不如在 ERP 上给你结。**所以我们其实是个消耗大户——因为你要**持续盯着**这东西，就持续消耗很大。"*
> *"这还不是'选便宜的'的问题。不同的场景不同的东西，**成本跟产出是有对应关系的**。……**给适合的场景用适合的模型，也是产品应该要考虑好的**，不是说用最贵的就是最好。"*

### 依赖项要显性化（01:34:34）

> *"为什么我要你们列那个依赖项出来？就是告诉领导，这个事情依赖上上下下，**你需要提供帮助、我们做 sponsor 把资源协调出来，而不是单靠我们两三个人搞**。"*
> 现状缺口（说话人 5，01:35:57）：*"**数据和分析模型现在都是缺的**，模型肯定是买的。"*

### 端到端剧本（建议作为验收演示脚本）

**E2E-1 「本项目自己」**（S10，已发生过的真实链路，最有说服力）：
拉启动会 → 建群（多数人只知晓）→ 内部小会 → 群里聊 + 单聊 + 发报告 → 大家反馈 → 再拉会 → 更新原型 → 第二轮稳定 → 转开发 → 群沉默。
**验收断言**：① 推进有结束、群没有结束，两者的生死不绑定；② 全程用户没有为了"喂系统"改变任何工作习惯；③ 最后能回答"这件事的每一次产物出自谁、出自哪次现场"。

**E2E-2 「下周一评审会」**（S3 + S4 + S5）：
派活 → 被拒（理由：本周做不来，下周评审会定）→ 改判"我自己来" → 子推进改写为"下周一评审会上确定" → 会开完 → 速记出纪要 → 系统扫到 → **不得直接判完成**，只能标"会上提到、未见产物" → 提示补设计方案 → 从 IM 关联进来 → 两勾齐 → 整条推进关闭。
**这条链同时压 C1–C4 四个硬约束**，是最容易暴露"跑不起来"的一条。

**E2E-3 「双账号派活」**（S2 + S9）：
A 账号派活 → B 账号收到协作请求（高亮）→ B 看到上下文 → B 在工作现场做完并交付 → 系统识别产物归属 → A 侧出现"已反馈" → A 打回一次 → B 改 → A 确认完成并归档。
**必须用两个真实账号**——会上被点名批评的正是"用一个账号讲两个视角"。

## §7 与本产品词表的对照（我做的翻译，会上没有这一层）

> **这一节是我的映射，不是会议结论。** 我核对过 `docs/终极形态设计方案.md`：**「工作现场」「订阅源」这两个词在我们的设计文档里一次都没有出现**——它们是对面那条线的词。反过来，我们的「场所」「证据面」「合环阀」「受领三态」「最小听众」「立此存照律」在他们那边也没有。两套词表指向的问题域高度重叠，翻译如下，供闭环验证时对齐用。

| 他们的词（本次会议） | 我们的对位物 | 差异要点 |
|---|---|---|
| **工作现场** | **场所**（design 出现 52 次） | 他们的"工作现场"包含"线下口头交办"这种无留痕的**沟通现场**（S9 第 6 问）——我们的"场所"是图内概念，图外交付走"人一句话补登"（v4.20）。**这是我们已裁决、他们还没裁决的地方。** |
| **订阅源** | **证据面 / 对象面**（design 2 次、私账层 5 次） | 他们的订阅源是**输入侧**清单（群/纪要/AI 产物/未来 ERP）；我们的证据面是**消费侧**（右栏归集锚对象）。两者是同一条链的两端，**我们缺一份显式的"输入源清单"**。 |
| **产物跟标准的校准**（D3） | **对表 / 合环阀**（design 13 次 / 3 次） | 概念同源。他们把它列为推进的三大职责之一，我们把它做成环行八环里的一环。 |
| **中等置信度 + "提到了但没看到产物"标记**（D4） | **立此存照律 + 证据分层**（私账层 13 次） | **这是本次转录里最值得直接借用的一条**：会议源的置信度分级，比我们现有的"证据门"更细一档。 |
| 接活人三种行为（接受/拒绝/要前置） | **受领三态**（design 3 次） | 我们的三态是"接受/拒绝/无回应"；**他们的第三态是"我要做但你先给我 X"**，这是一条我们没有的边。值得考虑是否入册。 |
| 改派别人 | **移交 = 边的重新签发**（design 17 次） | 我们已定稿（v4.24）：旧边 transferred 吸收态 + 新边出生带血缘、三方知情。**他们只有"改派"一个动作，没有血缘。** |
| 撤销 + 目标同步（D7） | **作废终态 + 目标枢纽**（design 5 次） | 我们已有"目标有死法（作废终态）"；他们的"撤了目标不改就永远完不成"正是同一个洞。 |
| 群里的提醒只应我可见（S6） | **最小听众 + 可见域**（design 3 次） | 同一条不变量。他们卡在"群内文件全员可见"的平台现状上——**这个现实约束我们也吃同一份**。 |
| 执行回工作现场（D2） | **执行入口统一律 / 传送门非表单**（v4.9） | 结论完全一致，是两条线独立收敛到同一裁决的一个强证据。 |
| 从建群那一刻就是推进的起点（S10） | **场所的出生故事 / 出生血缘携带语境**（v4.18） | 同源。他们提出"建群一般都有一个目标"，我们的 v4.18 已成文"从目标/承诺语境建群继承挂接"。 |
| 群没有结束、推进有结束（S10） | 我们尚无显式对位 | **值得补**：场所的生命周期与目标的生命周期不绑定，这句话在我们的设计文档里没有明写。 |
| "用了 vs 没用有什么区别"（§5） | **摩擦再分配 / 复利开双账**（v4.13 / v4.25） | 他们卡在回答不出差异；我们的答案是四分法 + 双账。**这是我们相对成熟的一块。** |

**三条可以直接吃进来的东西**：
1. **会议源置信度分级 + "提到了但没看到产物"标记**（D4）——比我们现有证据门更细，且有明确的 UI 形态。
2. **受领第三态"我要做但你先给我 X"**——我们的受领三态里没有这条边。
3. **"每个工作现场的证据形态不一样，要分别定义产生什么证据、存在哪、怎么检测"**（S5）——我们有证据面，但没有一张按场所分类的证据形态表。

**一条要警惕的**：他们把"执行感不够"当成产品问题，倾向用前端转圈圈/阶段性弹窗来补（52:11）。这条在我们的摩擦四分法下要过刀：**先问这个"感觉"缺失是不是在保护什么**。说话人 1 的判断反而更接近我们的立场——*"最终问责是我，所以产物是我产出的，不是灵基产出的。"*
